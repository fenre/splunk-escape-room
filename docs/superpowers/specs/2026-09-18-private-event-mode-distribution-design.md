# Private Event Mode Distribution

## Goal

Give an authorized internal operator a low-knowledge way to download and run the complete Nakatomi Heist Event Mode on a laptop.

The operator interacts with one launcher bundle. Internally, Docker Compose runs three private images:

- `splunk`: Splunk Enterprise plus the Nakatomi app, puzzle data, parsing configuration, player role, and account-seeding automation.
- `proxy`: the game, lobby, scenario files, HEC reverse proxy, and public HTTP entry point.
- `scoreboard`: the credential-free browser scoreboard backed by server-side Splunk searches.

This keeps the user experience simple without combining unrelated processes into one fragile container.

## Distribution Boundary

The derived Splunk image is restricted to employees covered by the organization's applicable Splunk agreement. Internal distribution is not assumed to grant redistribution rights.

Publishing is fail-closed:

1. The private-image workflow runs only by manual dispatch or an explicitly approved release.
2. The repository variable `SPLUNK_DERIVED_IMAGE_DISTRIBUTION_APPROVED` must equal `true`.
3. The workflow documentation identifies the person or process responsible for confirming that the applicable Splunk agreement permits this use.
4. GHCR packages remain private.

If authorization is absent, operators use the existing local-build path, which pulls the official `splunk/splunk` image directly from Docker Hub.

## License Acceptance

License acceptance is never baked into an image layer and is never implied by downloading the image.

The first-run launcher:

1. Shows links to the current Splunk General Terms and software license.
2. Requires an explicit typed or interactive confirmation.
3. Passes `SPLUNK_START_ARGS=--accept-license` and `SPLUNK_GENERAL_TERMS=--accept-sgt-current-at-splunk-com` only at runtime.
4. Records no acceptance credential or personal data in the image or repository.

Non-interactive execution requires an explicit `--accept-splunk-terms` flag. Omitting it fails before Docker starts.

## Operator Experience

The release contains:

```text
nakatomi-event-mode/
├── start.sh
├── start.ps1
├── stop.sh
├── stop.ps1
├── docker-compose.release.yml
├── .env.example
├── README.md
└── SHA256SUMS
```

First run:

1. Install Docker Desktop.
2. Download and extract the private release bundle.
3. Run `start.sh` on macOS/Linux or `start.ps1` on Windows.
4. Confirm Splunk terms.
5. Enter or accept generated admin/player passwords and event settings.
6. The launcher authenticates to GHCR if the images are not already available, pulls pinned images, starts the stack, waits for health, and prints/open URLs.

Subsequent runs reuse local secrets and Docker volumes. The launcher never prints the HEC token. The admin password is displayed only when newly generated or explicitly requested from the local environment file.

## Image Contents and Startup

The Splunk image derives from the pinned official `splunk/splunk` tag and includes:

- `nakatomi_heist/`
- puzzle seed logs
- Event Mode policy files
- player-role and search-limit configuration
- seed-data and player-account scripts
- version stamp and legacy-navigation configuration

Runtime volumes still hold mutable `$SPLUNK_HOME/etc` and `$SPLUNK_HOME/var`. The entrypoint copies immutable application/configuration content into a fresh volume, restores missing seed data, and creates player accounts after Splunk becomes ready.

Secrets enter through runtime environment variables only:

- `SPLUNK_PASSWORD`
- `SPLUNK_HEC_TOKEN`
- `PLAYER_PASSWORD`

No password, token, certificate, or license key is embedded in an image, Compose file, release archive, test fixture, or CI log.

## Registry and Versioning

GHCR image names:

- `ghcr.io/fenre/splunk-escape-room-splunk:<release>`
- `ghcr.io/fenre/splunk-escape-room-proxy:<release>`
- `ghcr.io/fenre/splunk-escape-room-scoreboard:<release>`

Release Compose uses immutable digest references generated by CI. Human-readable version tags are also published, but the downloadable bundle pins digests to prevent tag drift.

All images target `linux/amd64`, matching the Event Mode Docker policy and official Splunk image. Apple Silicon runs them under Docker's amd64 emulation.

## CI and Supply Chain

The private image workflow:

1. Checks out a tagged commit.
2. Runs Event Mode policy validation and application tests.
3. Builds all three `linux/amd64` images.
4. Generates an SBOM and provenance attestation for each image.
5. Scans images for critical vulnerabilities.
6. Pushes only when the authorization variable is present.
7. Resolves pushed image digests.
8. Renders `docker-compose.release.yml` with those digests.
9. Packages launcher files and checksums as a private release artifact.

GitHub Actions and Docker actions must be pinned to immutable commit SHAs before release.

## Failure Handling

- Missing Docker: launcher explains how to install/start Docker Desktop and exits.
- Terms not accepted: exits before pull/start.
- GHCR unauthorized: explains the required `docker login ghcr.io` flow without asking users to paste tokens into chat or logs.
- Unsupported platform: warns that only amd64 is supported; Apple Silicon emulation is allowed.
- Port conflict: prompts for alternate game/Splunk ports.
- Insufficient memory: warns below 8 GB available; recommends 16 GB.
- Failed health check: prints safe service status and bounded logs with secrets redacted.
- Existing incompatible Splunk volume: shows the version-stamp warning and offers a separately confirmed destructive reset.

## Verification

A release is complete only after:

1. Static Event Mode policy validation passes.
2. A clean-machine-style test pulls the private images without local builds.
3. Splunk Web and HEC become healthy.
4. Puzzle indexes contain expected minimum event counts.
5. the Nakatomi app and Facilitator Board are installed.
6. player accounts exist and cannot access the admin-only Facilitator Board.
7. the game, lobby, and public scoreboard are reachable.
8. telemetry posted through the proxy appears on the scoreboard.
9. image inspection confirms no embedded credentials.
10. release Compose contains digest-pinned images and no `build:` sections.

## Out of Scope

- Public distribution of the derived Splunk image
- Baked-in terms acceptance
- Baked-in credentials or license keys
- Native ARM Splunk images
- A single container running Splunk, nginx, and scoreboard processes
- Shared keypad state across player devices
